# 言語仕様

## 1. この言語を一言で説明すると

**複数バージョンのプログラムが共存して使われているプログラムを整合的に実行するための言語**

- 上流が与えた互換仕様に基づき、版ごとの個別操作を**単一の論理操作として扱う**。
  - 論理操作として統合された呼び出しは、振る舞いの差を外部に露出させずに実行される。
  - これは、この言語における観測的等価性に基づく。
- この仕様では、互換仕様から生成された論理操作を、現在の実行状態で実現可能かを検査しながら実行する。

## 2. 誰が何をできる言語なのか

ステークホルダーは、ライブラリ開発者と、それを使用する下流のソフトウェア開発者である。

### 2.1 ライブラリ開発者

ライブラリ開発者は、次のことを行う。

1. 通常通り `v1`, `v2` のプログラムを作成する。
2. 各版の呼び出しについて、**観測的等価性を満たす呼び出し方の対応**を互換仕様として作成する。
   - 例: `v1` の `a()` ≃ `v2` の `exp; a(arg)`
   - ここから作成される論理操作を呼び出す前提条件が必要な場合もある。
   - 例: `v2` 側の状態 `s` が存在する場合のみ。
3. 各版のプログラムと互換仕様を専用フレームワークに入力する。
   - ここではコンパイラとして実装する。
4. 単一の論理モジュールを取得し、これを頒布する。
   - 下流の開発者はその単一の論理モジュールを使用する。
   - 今回はモジュールを基本単位とする。その中にクラスが含まれてよい。

### 2.2 下流のソフトウェア開発者

下流のソフトウェア開発者は、基本的にバージョンを意識せずにプログラムを書ける。

ここで「バージョンを意識しない」とは、コード上に明示的なバージョン指定が必要ないという意味である。

ただし、ソースコード上には旧版的な呼び出しと新版的な呼び出しが混在してよい。

- ある部分では旧 API を使っている。
- 別の部分では新版で追加された API を使っている。

互換仕様によって論理操作化された呼び出しは、版差が吸収されて実行される。

観測的等価な他版のプログラムがない呼び出しも、論理操作化されている場合がある。例えば、削除・追加されたメソッドである。

その操作は特定版の意味しか持たないが、実行時には前提条件を確認し、必要なら状態調整を行う。

## 3. 互換仕様と論理操作

互換仕様は、各版の呼び出し方について、観測的等価性を満たす対応を記述するものである。

```text
v1: a()
v2: exp; a(arg)
logical operation: a
```

互換仕様から生成される実行単位を論理操作と呼ぶ。

論理操作には、複数版の観測的等価な呼び出し列を統合したものと、特定版の意味しか持たないものがある。

互換仕様は、例えば次のような情報を持つ。

- 論理操作の識別子
- 対象となる版
- 各版で対応する呼び出し形または呼び出し列
- 呼び出しがどの版の意味を期待しているかを判断する条件
- 観測的等価な実行列を選ぶ条件
- 実行前に必要な状態前提
- 必要な状態調整
- 実行継続時に危険箇所として報告する条件

複合的な API 変化がある場合も、原子的な変化の分類を実装の正本にはしない。

例えば、ある関数の名前と本体が同時に変わった場合、それを名前変更と本体変更の合成として実装するのではなく、1つの論理操作として互換仕様を書く。

```text
logical operation: user_name
v1: get_name(user)
v2: name_of(user)
meaning resolution:
  user の状態から、どちらの意味を期待しているかを判定する
realization:
  必要なら user.profile を初期化してから実行する
```

この論理操作を実現するために、互換仕様は「呼び出し元モジュールで判断する」「オブジェクトの状態で判断する」「履歴で判断する」などの機能を組み合わせる。

利用できる機能は [互換仕様の機能カタログ](compatibility-features/README.md) に置く。

## 4. 整合的に振る舞うの定義: 観測的等価性を満たす

通常の観測的等価性では、外から観測できる振る舞いが同じなら、内部実装が違っても同じプログラム片とみなす。

この言語での観測的等価性では、外から観測できる振る舞いが厳密に同じである必要はない。

- 返り値や状態の内部表現が異なる場合もある。
- それが後続の論理操作を通して整合的に利用できればよい。

この言語では、**論理操作による実行部分では振る舞いの差が外部に露出しない**ことを要求する。

外部 I/O や副作用のように観測差が露出しやすい処理では、互換仕様がどの観測を同一視するか、または危険箇所として報告する条件を明示する。

## 5. 特徴的な機能: 呼び出し実現機構

呼び出し実現機構は、互換仕様から生成された論理操作を、現在の状態で実現できるかを検査しながら実行する機構である。

### 5.1 三つの機能

1. **その呼び出しがどの版の意味を期待しているかを決定する。**

   `x@v1`, `x@v2` がこの言語の意味での観測的等価性を外れる場合、この判定が必要になる。

   例:

   ```text
   v1: x()
   v2: y(); x()
   ```

   この場合、`x()` が `x@v1` なのか `x@v2` なのかを状態や文脈から判断する。

   - `y` がやっている処理が未実行だと分かるなら `x@v1`
   - `y` がやっている処理が実行済みだと分かるなら `x@v2`

   ここで使える条件を増やしていくことが、コンパイラ実装の拡張になる。

   - 呼び出し元のモジュール
   - オブジェクトの現在状態
   - それまでに実行された操作の履歴
   - 特定フィールドの有無
   - 初期化済みフラグ
   - 引数の形・フォーマット

2. **観測的等価な各版の実行列のうち、どちらを呼ぶかを決定する。**

   実行状態によっては、ある版に固定した計算しかできないこともある。

   例:

   ```text
   MD5 ハッシュ値だけが存在する状態
   SHA ハッシュ値を要求する実行列
   ```

   この場合、SHA 側の実行列はそのままでは選べない。

3. **選択した実行列を実行するために必要な状態に調整する。**

   選択した実行列に必要な状態が現在状態に存在しない場合、互換仕様に従って状態を調整する。

   状態調整には、別版の状態表現を生成する、特定フィールドを初期化する、状態のバージョンを揃える、履歴やフラグを更新する、といった処理が含まれる。

### 5.2 全体フロー

呼び出し実現は次の流れで行う。

1. `x()` や `obj.x` が対応する論理オブジェクトを呼ぶ。
   - これは基本的に Python の名前解決や属性アクセス機構に任せる。
2. 必要なら、その呼び出しがどの版の意味を期待しているかを解決する。
3. 必要なら、現在状態から実行可能な観測的等価なプログラムを選ぶ。
4. 必要なら、その前提を満たすように状態を調整する。
5. 呼び出しの実体に処理を委譲して実行する。
6. 途中で引っかかる場合は、不整合の可能性を承知で実行を進めるか、危険な箇所として報告する。

## 6. 危険箇所

危険箇所は、互換仕様に基づく実行が整合的であると保証できない可能性のある箇所である。

この言語では、危険箇所でただちに停止することを基本にはしない。実行は継続し、どこで呼び出し意味の判断、実行列選択、状態調整、観測的等価性に不確かさがあったかを診断情報として報告する。

危険箇所として報告する対象には、少なくとも次がある。

- 呼び出しが期待する版の意味を一意に判断できない
- 観測的等価な実行列を選べない
- 必要な状態前提を満たせない
- 状態調整が不完全である
- 外部 I/O や副作用により観測的等価性が崩れる可能性がある

## 7. 想定される疑問と回答

### Q1. 何が嬉しいのか

**ソースコード上には複数の版が混在したまま**、あたかも単一の版で実行したかのように見えるのが嬉しい。

正確には、単一の論理操作による一貫した意味で実行できる。

また、論理操作外での計算や、状態調整に不確かさがある箇所を危険箇所として報告できる。これにより、「ここまでの移行作業は正しいか？」を確認できる。

### Q2. 単に与えられた互換仕様を用いてコードを静的に変換すればよいのではないか

この言語は、静的に変換できないケースを考えている。

Python のような動的型付け言語だと、呼び出し対象や引数の形が実行時まで決まらないことがある。

また、実行時の状態を確認する必要がある。

- 共有オブジェクトが新旧を行き来する場合
- 引数の形やフォーマットから呼び出し意味を判断する場合
- 履歴や初期化済みフラグを見ないと状態前提を判断できない場合

そのため、この言語では互換仕様から生成された論理操作を、実行時の状態や文脈に基づいて実現する。
